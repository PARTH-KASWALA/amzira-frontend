Product and Architecture Decisions1. The first seller role is the existing backend `admin` role. A narrower warehouse/support role is post-launch work.2. Seller routes are `/seller/login`, `/seller/orders`, and `/seller/orders/[id]`.3. Seller routes do not appear in public storefront navigation.4. The frontend role check controls presentation only. Every seller API request must still pass backend `require_admin` authorization and the production IP allowlist.5. Because API cookies belong to the API origin, the first release uses a client-side seller guard plus backend authorization. A Next.js middleware check must not pretend to authorize a cookie it cannot reliably read.6. The canonical order list/detail contract lives under `/api/v1/admin/orders`.7. One backend service must own all order transitions. Duplicate direct-update behavior must be removed or delegated to that service.8. Delivered orders must use logic that records `delivered_at` and starts the published return window.9. Cancelling an unpaid order must restore reserved/deducted stock at most once. Cancelling a paid order must follow an explicit refund workflow; a status label alone must never substitute for a refund.10. COD stays disabled unless the cleanup defect, payment state, stock policy, and acceptance tests are closed.11. A backend checkout enable flag is required. The frontend displays an honest maintenance state when checkout is disabled, while the backend independently rejects payment-order creation.## 4. Functional Requirements### Authentication and authorization**FR-AUTH-001:** While an admin session is valid, when the administrator opens `/seller`, the system shall allow access to the seller panel.**FR-AUTH-002:** When a guest opens a seller route, the system shall redirect to `/seller/login` and preserve the intended seller destination.**FR-AUTH-003:** When an authenticated customer opens a seller route, the system shall show an access-denied state and shall not request or render admin order data.**FR-AUTH-004:** When any user requests an admin API, the backend shall verify the current database role, active session, session version, CSRF boundary for mutations, and production IP policy.### Order queue and detail**FR-ORDER-001:** While an administrator is authorized, when `/seller/orders` loads, the system shall show a server-paginated order queue sorted newest first.**FR-ORDER-002:** When the administrator filters by fulfilment or payment status, date, order number, customer name, email, or phone, the backend shall return only matching orders with bounded pagination.**FR-ORDER-003:** When an administrator opens an order, the system shall show the order number, customer contact, delivery address, items and variants, quantities, totals, coupon, payment state, fulfilment state, courier, tracking, ETA, timeline, customer notes, and admin notes.**FR-ORDER-004:** When no matching orders exist, the system shall show a useful empty state without fabricating data.### Fulfilment and tracking**FR-FULFIL-001:** While an order transition is valid, when an administrator submits the next state, the backend shall update the order and append an actor-attributed history event in one transaction.**FR-FULFIL-002:** When an invalid or stale transition is submitted, the backend shall reject it without changing the order, stock, payment, or history.**FR-FULFIL-003:** When a courier, tracking number, tracking URL, AWB, or ETA is recorded, the backend shall persist it and expose it to both the seller detail and customer tracking responses as appropriate.**FR-FULFIL-004:** When an order becomes delivered, the backend shall record delivery time and calculate the return deadline exactly once.**FR-FULFIL-005:** When an eligible unpaid order is cancelled, the backend shall restore deducted/reserved stock no more than once.**FR-FULFIL-006:** While an order is paid, when cancellation requires a refund, the system shall require the refund workflow and shall reconcile the final state through Razorpay rather than marking the order refunded locally.### Payment and inventory integrity**FR-PAY-001:** When Razorpay verification or a signed captured-payment webhook succeeds, the backend shall create at most one paid order for that payment.**FR-PAY-002:** When payment verification fails, expires, or carries an invalid signature, the backend shall not create a paid order.**FR-PAY-003:** When checkout reserves inventory, the backend shall prevent stock from becoming negative under concurrency and shall release expired reservations exactly once.**FR-PAY-004:** When a captured payment arrives after its stock reservation was released, the backend shall reject fulfilment and issue/reconcile a compensating refund.### Checkout safety control**FR-SAFE-001:** While checkout is disabled, when a customer attempts to create a payment order, the backend shall return a safe unavailable response without reserving stock or creating a payable order.**FR-SAFE-002:** While checkout is disabled, the frontend shall keep the catalog available and display a clear temporary checkout-unavailable message.## 5. Non-Functional Requirements### Security and privacy- Backend authorization is mandatory; client role state is never authority.- Seller pages use `Cache-Control: private, no-store, max-age=0`, `noindex`, and robots exclusions.- No payment secrets, auth tokens, webhook secrets, database credentials, or unnecessary PII enter frontend code, browser storage, URLs, analytics, or logs.- Seller mutations retain CSRF protection and must not retry automatically after an ambiguous network failure.- Admin IP policy must be tested from the actual launch network or a stable VPN egress address.- Admin credentials must be unique, rotated after bootstrap, and not shared with customer accounts.### Reliability- Order mutations are idempotent from the operator's perspective.- Seller screens distinguish loading, empty, unauthenticated, forbidden-role, forbidden-IP, validation/conflict, server error, and timeout states.- A failed mutation retains entered courier/tracking/note values for a safe retry.- The order page refreshes authoritative state after every successful mutation.- List queries use eager loading and bounded pagination to avoid N+1 growth.### Performance and accessibility- Seller list API target: p95 under 500 ms for the initial launch volume.- The order queue remains usable at 375 px and desktop widths without hidden required actions.- Every control has an accessible name, visible keyboard focus, and a minimum 44 px touch target.- Status and error messages are announced; status is never represented by color alone.## 6. AC-008: Payment idempotencyGiven one captured Razorpay paymentWhen the callback and webhook are replayedThen one paid order existsAnd stock is decremented/reserved only once.### AC-009: Failed payment
